Set this repository's site up with Tonen, so people can comment on it while it runs.
Your member may not be a developer: before each step, say in one plain sentence what you're about to do and why; never ask them to run a command; when their browser opens, tell them what to click there; and end with what they can do now.
1. Look first: what the project is built with, the address its dev server runs at, and any deployed address (production, staging, a pull request's preview) with the git branch that runs there: production runs the default branch, main unless the repository uses another. Call `tonen_cli` with `status`: whether this computer is signed in to Tonen, and whether this repository has a project already.
2. Comments, who can comment, the share link and the reviewers belong to a branch, the same at every address it runs at. Ask them once who should comment on the default branch: do people outside their team use it for real? Yes: `people`, where only the people they add can comment; no (a prototype, a project still in the making): `anyone`, where anyone who opens it can, after confirming their email. Ask too who should comment on a new branch, such as one a teammate checks out or a pull request's preview: a branch the plugin reports starts at `anyone`, and runs only on their computers until an address has it.
3. Call `tonen_cli` with `init`, the dev server's address as `address` (or the deployed one, when there's no dev server; whole, with the folder it's published under) and their answer for the default branch as `access`. Its first call may open their browser to sign in to Tonen: tell them. It names the project in tonen.json at the repository's root: tell them to commit it, so their team and Claude find the project too. Add the script tag where the answer's `install.where` says, unless `edited` names the file it went into, always, also when the project only runs on this computer: a teammate who runs it gets the bar too, with the comments of the branch they have checked out. Add the CSP sources if the project sets a Content-Security-Policy. For every other deployed address, `tonen_cli` with `addresses_add`, the address and its `branch` (left out: the default branch), and for a branch the project doesn't have yet their answer as `access`. If they already have a project for this repository on Tonen, `tonen_cli` with `link` and its id instead of `init`.
4. Each deployed address waits for them to confirm it, and until then Tonen doesn't run there: give them the link the answer gives (the project's page in Tonen), ask them to confirm it there now in their browser, and call `tonen_cli` with `branches` until it no longer waits before you say it's done.
5. Start the dev server if it isn't running, then call `share_local_site` with its port, so people elsewhere open it too. It shows the branch this repository has checked out, with that branch's comments, and follows when they switch. Only the project's members and the people they add to that branch get in, whatever the branch's setting: it's their own computer. The first time, their browser opens to confirm sharing: tell them.
6. Tell them, in a few short lines: open the shared address (it signs them in with one click) and press C to comment on anything; that the same address works for the people they add to the branch, while this session runs; and what's next: /tonen:add-reviewers asks people to comment by email, and /tonen:fix works through what they comment. The first time they want comments fixed, or @Claude to answer them on the project, Claude Code asks them to sign in to Tonen once: they type /mcp, pick Tonen, then Authenticate.

Tell your member, so they can tell their team.
